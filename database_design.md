# Database Design - Gans Scooter Demand Pipeline

## Overview

The Gans database is designed to support scooter positioning decisions by combining multiple data sources:

- City information collected through web scraping
- Weather conditions retrieved from the OpenWeather API
- Airport and flight arrival information retrieved from the AeroDataBox API
- Scooter demand forecasting based on combined analysis

The purpose of the database is to combine **location data, weather conditions, and airport activity** to support better scooter allocation decisions.

---

# Database Architecture Diagram (ERD)

The database architecture was created using MySQL Workbench.

The database contains six main tables:

| Table | Purpose |
|---|---|
| `cities` | Stores city information collected through web scraping |
| `weather` | Stores historical weather records |
| `weather_current` | Stores the latest weather conditions |
| `airports` | Stores airport information retrieved from AeroDataBox |
| `flights` | Stores arriving flight information retrieved from AeroDataBox |
| `scooter_weather_forecast` | Stores scooter demand forecast results based on combined data analysis |

# Table Relationships

## 1. Cities → Weather

### Relationship

```
cities (1)
    |
    |
weather (many)
```

### Explanation

A single city can have multiple weather records because weather data can be collected at different points in time.

Relationship:

- Primary Key:
  - `cities.city_id`

- Foreign Key:
  - `weather.city_id`

Example:

A city can have many weather observations collected from the OpenWeather API.

---

# 2. Cities → Weather Current

### Relationship

```
cities (1)
    |
    |
weather_current (many)
```

### Explanation

A city can have multiple current weather records as the API is queried repeatedly.

Relationship:

- Primary Key:
  - `cities.city_id`

- Foreign Key:
  - `weather_current.city_id`

The latest weather record represents the current environmental condition used for scooter demand analysis.

---

# 3. Cities → Airports

### Relationship

```
cities (1)
    |
    |
airports (many)
```

### Explanation

A city can contain one or more airports.

Relationship:

- Primary Key:
  - `cities.city_id`

- Foreign Key:
  - `airports.city_id`

Airport information is retrieved through the AeroDataBox API and connected to its corresponding city.

---

# 4. Airports → Flights

### Relationship

```
airports (1)
       |
       |
    flights (many)
```

### Explanation

One airport can receive many arriving flights.

Relationship:

- Primary Key:
  - `airports.airport_id`

- Foreign Key:
  - `flights.airport_id`

Flight arrival information is retrieved from AeroDataBox and linked to the airport where arrivals occur.

---

# 5. Cities → Scooter Demand Forecast

### Relationship

```
cities (1)
       |
       |
scooter_weather_forecast (many)
```

### Explanation

A city can have multiple scooter demand forecasts generated at different times.

Relationship:

- Primary Key:
  - `cities.city_id`

- Foreign Key:
  - `scooter_weather_forecast.city_id`

The forecast is generated by combining:

- Weather conditions
- Airport arrivals
- Location information

# Database Tables

---

# 1. Cities Table

## Purpose

The `cities` table stores geographical information collected through web scraping.

The latitude and longitude values are used to query external APIs.

## Columns

| Column | Description |
|---|---|
| city_id | Primary key. Unique city identifier |
| city_name | Name of the city |
| country | Country name |
| latitude | Geographic latitude |
| longitude | Geographic longitude |
| country_code | Country identifier |
| city_timezone | City timezone |
| date_retrieved | Date the data was collected |

## Relationships

The `cities` table is the central reference table.

It connects to:

- Weather data
- Current weather data
- Airport information
- Scooter demand forecasts

---

# 2. Weather Table

## Purpose

The `weather` table stores historical weather information retrieved from the OpenWeather API.

Weather conditions are one factor used to understand scooter demand.

## Columns

| Column | Description |
|---|---|
| weather_id | Primary key |
| city_id | Foreign key linked to cities |
| temperature | Temperature value |
| feels_like | Perceived temperature |
| humidity | Humidity percentage |
| weather_description | Weather condition description |
| wind_speed | Wind speed |
| date_retrieved | API retrieval timestamp |

## Relationship

```
cities (1)
    |
    |
weather (many)
```

---

```
airports (1)
      |
      |

```

---

# 6. Scooter Weather Forecast Table

## Purpose

The `scooter_weather_forecast` table represents the business output layer.

It stores scooter demand predictions generated by combining multiple factors:

- Weather conditions
- Airport arrivals
- Location information

This table supports scooter positioning decisions.

## Columns

| Column | Description |
|---|---|
| forecast_id | Primary key |
| city_id | Foreign key linked to cities |
| weather_risk | Weather impact assessment |
| scooter_demand_forecast | Predicted scooter demand level |
| notes | Explanation of forecast |
| date_retrieved | Forecast generation timestamp |

## Relationship

```
cities (1)
       |
       |
scooter_weather_forecast (many)
```

# Business Logic

The database supports scooter demand analysis by combining:

```
City Location
+
Weather Conditions
+
Airport Arrivals

        ↓

Demand Analysis

        ↓

Scooter Demand Forecast

        ↓

Scooter Positioning Decision
```

# Example Decision Logic

## High Demand Scenario

Conditions:

- Many arriving flights
- Good weather conditions
- Low wind
- Suitable riding conditions

Decision:

Increase scooter availability near airport locations.

---

## Low Demand Scenario

Conditions:

- Heavy rain
- Strong wind
- Poor riding conditions
- Lower arrival activity

Decision:

Adjust scooter allocation.
